# KEPT audit (2026-11-26)

Multi-agent audit of the KEPT repo at commit afb1f0c, against the friend's 7 open concerns. Every critical/high finding was checked by 2 adversarial reviewers.

## Overall

VERDICT: The Devnet program's money logic works. The app's Live mode cannot use it today, so the core "stake, escrow, payout" demo cannot run through the app right now. Seven audits agree on this, and adversarial reviewers confirmed every critical/high finding.

WHAT IS PROVEN (by running something):
- The SPL/test-SKR escrow on Devnet program 6iXXBqsd… really did create, join, start, record_checkin, settle, claim and sweep_held for 4 Oaths on 2026-10-11. All vaults are now 0. The treasury holds exactly 818.333336 SKR, and the payouts match a JS port of replay_v3 that passes all 14 engine vectors. Those runs came from the friend's script (onchain/scripts/e2e_devnet_v3.ts) using the upgrade-authority key. They never went through the app. Reviewers found no theft bug in the deployed SPL path.
- All test suites that can run here pass at HEAD afb1f0c: frontend jest 33 suites / 475 tests, backend 86, engine 24, chain 7, shared 3. Typecheck and lint are clean and GitHub CI is green.
- Demo and Live are cleanly separated. No mock code is reachable from the Live path.
- Backend sign-in rejects replayed and forged tokens.

WHAT IS BROKEN:
1. The app cannot create an Oath in Live. realTx.ts:28-37 only builds create_oath_sol. The deployed binary (sha256 8b8746…, last deployed 2026-10-11) has none of the five *_sol instructions; simulating the app's own instruction returns error 101. The flag EXPO_PUBLIC_LIVE_NATIVE_SOL_OATHS=0 hides this behind a "Live Oaths unavailable" screen. The published v1.1.1 used an SPL create path that HEAD removed in a2a5626.
2. The hosted Render backend is a 2026-10-09 build (commit b1d9cdc, not in this repo). It predates rules v3, the per-habit proof routes and the SOL price field, so Live proof most likely fails at the challenge step even for legacy Oaths.
3. Proofs can be forged with three plain HTTP calls and no photo. The server trusts the phone's verdict. An in-process PoC produced a record_checkin signed by the verifier for the attacker.
4. Non-Seeker wallets can stake a solo Oath, but every proof route then returns 403 (requireGenesis at backend/src/routes/v4.ts:80, which I spot-checked). The stake would be lost. Today the flag hides this, but it bites as soon as the flag is turned on.
5. One key, FFAZTtBd…, is upgrade authority, Config admin, the only possible check-in verifier and mint authority. It is not on this laptop, and there is no instruction to change the verifier. Without the friend's key you cannot run check-ins or upgrade this program ID. Your options are to get the key, or deploy your own copy under a new program ID.

## Concern status
- **On-chain escrow: staking and payouts correct on chain**: partly-working. The SPL test-SKR escrow is proven on Devnet, but only by the friend's script on 2026-10-11, never through the app. The vaults drained correctly, the treasury holds exactly 818.333336, and payouts match the engine (14/14 vectors). The native-SOL instructions the app now uses are not deployed. Design risks remain: creator-only start/cancel can lock joiners' stakes, one key controls everything, and a group break means a 100% loss.
- **Public Oaths: create, join, prove, claim on Devnet**: broken. The flow cannot even begin in Live. The app only builds create_oath_sol, which the deployed program lacks (simulated: error 101), and the flag is 0. The hosted backend is also a pre-v3 build without the per-habit proof routes.
- **Invites: join by link, QR or code**: broken. The code plumbing is correct on reading: generate and resolve codes, parse links/QR, build join_oath for the right Oath account. Android App Link verification passed on the phone. But no Oath can be created in Live to invite people into, and no Oath on Devnet has ever been joined through an invite. Invites are also not enforced on chain, never expire, and non-Seeker invitees get a raw 403 toast.
- **Proof checks: fakeable by a modified app**: broken. Confirmed and worse than feared. No modified app is needed: three plain HTTP calls with a made-up verdict and a random hash produce a record_checkin signed by the verifier (in-process PoC). No server-side image check exists anywhere. Bounty payouts are forgeable the same way.
- **Wallet signing and Seeker verification on device**: partly-working. MWA and sign-in code look correct, and the backend auth was verified by running it, but nothing has been tested on a device. Real Seeker Genesis verification cannot work on Devnet: the check reads Devnet, while the token lives on mainnet, so on Devnet 'verified' means 'on SGT_MOCK_ALLOWLIST'. The Genesis gate also blocks solo proof for non-Seekers.
- **Tests: 'some frontend tests failing'**: partly-working. I could not reproduce any failure: frontend 475/475, backend 86/86 and packages 34/34 pass, and CI is green. However: on-chain tests crash on Node 24 and need an uninstalled toolchain; backend and on-chain tests are not in CI; a known flaky jest test exists; and the v1.2.0 Release APK job failed, so the download link still serves v1.1.1.
- **Demo vs Live: proof of real staking, escrow, payouts**: broken. Demo/Live separation is clean, and Live shows chain payouts after settlement. But on HEAD the app cannot stake anything in Live. The only real escrow evidence is the friend's scripted SKR runs on 2026-10-11.

### [high] Server trusts the phone's proof verdict, so any member can 'keep' every day with three HTTP calls and no photo
- Verification: confirmed; side: backend
- Where: backend/src/routes/proofVerify.ts:16-61 (verdict fields from req.body, proofHash just 64 hex characters, photo never uploaded); backend/src/v4/verdict.ts:17-19; backend/src/v4/rules.ts:80-99; backend/src/routes/v4.ts:227-291 (habit then verifier-signed record_checkin); onchain lib.rs:232-250 (trusts verifier signature only)
- What happens: Sequence: sign in, then POST /api/proof/challenge (the response tells you the object and gesture), then POST /proof/verify with a made-up passing verdict, then POST /api/proof/habit. The last habit triggers record_checkin signed by the verifier. This was proven in-process with real createApp() routes and stubbed DB/RPC (scratchpad/audit/proof/forge_poc.test.mts). Because rules v3 pays miss penalties to keepers, a cheater collects part of honest members' stakes. Related weaknesses: OPEN_API_KEY is documented but read by no code, and parseVerdict is dead code (PROOF-7). A verification sent without Oath/day context can be redeemed on any Oath, and the challenge is matched only by gesture text (PROOF-6). There is no hash or photo dedupe (PROOF-5). The creator can set a free-text object such as 'hand' (PROOF-8). Mitigations: it needs a Genesis or allowlisted wallet and Oath membership; verification IDs are single-use and wallet-bound; it is Devnet only; it is an accepted trade-off in D-90. Also covers OATH-5 and PROOF-1.
- Fix: Make /proof/verify require the base64 photo (express.json already allows 12mb). Compute sha256 on the server and ignore the client's hash and verdict. Call the vision model on the server with OPEN_API_KEY, wired into config.ts, and validate with the existing parseVerdict and verdictPasses. Require oath, dayIndex and habit; return a challengeId and bind it. Add a unique index on wallet+proofHash. Restrict habitObjects to the catalog. Keep the on-device check as a pre-filter. Re-run forge_poc as a regression test. If there is no time, disclose 'proofs are checked on device and not yet re-verified on the server' in the pitch.
