## 8. How proof works (Live), from the current code

Sources: app `frontend/src/api/http/oaths.ts`, `frontend/src/screens/proof/Proof.tsx`, `frontend/modules/kept-gesture/`; backend (read-only) `backend/src/routes/proofVerify.ts`, `backend/src/routes/v4.ts` (`/api/proof/challenge`, `/api/proof/habit`), `backend/src/v4/rules.ts`.

1. **Challenge.** For each habit, the app asks `POST /api/proof/challenge` (Oath, day, habit). The server checks the wallet is a member and the day is open, then issues a hand gesture for that habit, valid for 2 minutes.
2. **Photo and check, on the phone.** The camera takes a live photo (no gallery picker in the app). The native module computes the photo's SHA-256 and runs MediaPipe (gesture) and Gemma (object, and whether it looks like a screen or printout) on the phone. **The photo is not uploaded.**
3. **Verdict.** The app sends `POST /proof/verify` with the photo hash, the expected object and gesture, and the model's verdict fields. The server stores the row and marks it PASS or FAIL by the verdict. It returns a one-time verification ID for a pass.
4. **Record.** `POST /api/proof/habit` claims that ID and records the habit. When every habit of the day has a photo, the backend's verifier key sends `record_checkin` on chain with `sha256` of the photo hashes in habit order.

**What is stored.**
- **On the server:** each check (wallet, photo hash, expected object and gesture, the model's verdict and reason, Oath / day / habit, pass or fail, when it was used); each proven habit (Oath, wallet, day, habit, photo hash, object); and the day's combined hash and check-in signature.
- **On chain:** the member's kept-days bitmask and the day's combined proof hash.
- **On the phone:** the photo file stays in the app's private cache. The app does not delete it explicitly.

**Replay protection that exists.**
- The gesture challenge expires after 2 minutes, with a 1-minute upload grace.
- A verification ID expires after 10 minutes, belongs to one wallet, can be used once (a conditional database update), must match that habit's object and gesture, and must be for that Oath, day and habit.
- A habit can be recorded only once per day (unique `oath, wallet, day, habit`).
- There is a limit of 20 checks per wallet per UTC day, and Genesis-token-gated access.

**What it does not do.** The server never sees the photo, so it **cannot verify the verdict**. It accepts the phone's result: a modified client could submit a passing verdict for any photo. Server-side checking is open as `docs/BACKEND_GAPS.md` P0-1. Model accuracy per object has not been measured (P1-26). `record_checkin` still accepts proofs for days after a break until the Oath settles; the settlement replay ignores them (P0-12).

**Review and appeal paths.**
- **Live habit proofs:** there is **no** group review. After 3 failed checks of a habit, the app ends on "3 failed checks is final. Today counts as missed." (`Proof.tsx`; P1-27).
- **Backend group review:** the review routes (`GET /api/oaths/:oath/reviews`, `POST /api/reviews/:id`) exist only for the legacy one-proof-per-day flow. That flow **does upload the photo**, which is deleted when the group decides or after 48 hours. The current app does not use it in Live.
- **Bounty proof in Live:** not available; the app shows "Check unavailable".
- There is no other appeal path.
- In Demo, the group review flow is simulated.
