## 0. Check it in five minutes

1. Download `KEPT.apk` from the [v1.4.2 release](https://github.com/ekanshvcpkg/KEPT-DAPP/releases/tag/v1.4.2) and run `sha256sum KEPT.apk`. You should get `7c30ee6c72f0b9d17b971fa9d65d705d6b43937bafbd75a8b7966e0623b55e71` (§1).

## 4. Devnet evidence: whole-workflow runs

`backend/scripts/e2e_all_habits.ts` runs this repo's backend locally against a local Postgres. It sends **real transactions to the program on Devnet**, signed with the real verifier key. Three things in it are stand-ins:

- the vision judge, which passes every photo unless its bytes contain `FAIL`;
- the rep sets, which are synthetic: a 3D body model "filmed" from several angles (`packages/engine/src/reps3d.fixtures.ts`);
- the receipt store and the voice: Supabase and ElevenLabs are turned off.

So these runs test the server, the rep recount, the program and the money. They don't test the AI judge or the phone; §5 covers those. Their receipts stayed in the local database and were never published, so you can check their on-chain side but you can't download their receipts. The script ran the re-hash check itself.

## 6. Audit a receipt yourself

This uses Oath A's day 0 from §5. You need `curl`, `sha256sum`, `xxd`, `base64`, `grep` and `cut`; one optional step uses `node`.

```bash
API=https://kept-api-vxk8.onrender.com
RCPT=https://bfcmapfznufzfbiyvcmx.supabase.co/storage/v1/object/public/keeper-receipts/receipts

# 1. What the server says this day put on chain: the receipt hashes (in habit order),
#    their combined hash and the record_checkin signature.
curl -s "$API/keeper/oaths/E88oqoakK6jsjfUmFeD885ibubMums92rXs6AZV4gqy5/days/0?wallet=EnD2dXFruNSTBTrZsmVT2wtDuewATAvo2hfoNqwun6hg"

# 2. Re-hash each receipt. The public file is the receipt's canonical JSON, byte for byte,
#    so sha256sum prints the file's own name.
curl -s "$RCPT/0e4f079822a50ec513d6543577f400b71cf2859a4645a01b39d120507f1c1c32.json" | sha256sum
curl -s "$RCPT/4d7f19af8d6db05d8792041e13497e0e3f19e0b179a2886e33485831c3a25218.json" | sha256sum

# 3. Combine them in habit order: SHA-256 of the raw 32-byte hashes, joined end to end.
echo -n 0e4f079822a50ec513d6543577f400b71cf2859a4645a01b39d120507f1c1c32 4d7f19af8d6db05d8792041e13497e0e3f19e0b179a2886e33485831c3a25218 \
  | tr -d ' ' | xxd -r -p | sha256sum
# df8a24d7bf1a6bfc8af1db78029f966ac587d602ea87917cd6f3cbaaf56345f9

# 4. Read proof_hash from the chain. The record_checkin transaction (4QUjW251…) logs a "Program data:" line.
#    It is Anchor's CheckinRecorded event, in base64: an 8-byte discriminator, oath (32), member (32),
#    day (1), then proof_hash (32).
curl -s https://api.devnet.solana.com -X POST -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"getTransaction","params":["4QUjW25194BXoJyrZbMPzdejtpK396tnXJJHKK3apSUG3rdifxFsAdsHfMkLpMngVnvp1Lm1svNHiCkH6mMNKrP7",{"encoding":"json","maxSupportedTransactionVersion":0}]}' \
  | grep -o 'Program data: [A-Za-z0-9+/=]*' | cut -d' ' -f3 | base64 -d | xxd -p -s 73 -l 32 -c 32
# df8a24d7bf1a6bfc8af1db78029f966ac587d602ea87917cd6f3cbaaf56345f9
```

**Through the API instead of the public file.** `GET $API/keeper/receipts/<hash>` returns `{ receipt, receiptHash, memoSignature, publicUrl }`. To hash `receipt` yourself, write it as canonical JSON: object keys sorted at every level, no whitespace, `undefined` values dropped (the same rule as `canonicalJson` in `packages/chain/src/keeper.ts` and `backend/src/v4/keeper.ts`). Then take the SHA-256:

```bash
curl -s "$API/keeper/receipts/05de54fe64e27cdc7a5ad58d5722dab53cc05459391f5ad1035445145fc7e46c" | node -e '
const c=v=>v===null||typeof v!=="object"?JSON.stringify(v):Array.isArray(v)?"["+v.map(c).join(",")+"]":"{"+Object.keys(v).filter(k=>v[k]!==undefined).sort().map(k=>JSON.stringify(k)+":"+c(v[k])).join(",")+"}";
let s="";process.stdin.on("data",d=>s+=d).on("end",()=>console.log(require("crypto").createHash("sha256").update(c(JSON.parse(s).receipt)).digest("hex")))'
# 05de54fe64e27cdc7a5ad58d5722dab53cc05459391f5ad1035445145fc7e46c
```

**For a failed verdict** there is no `record_checkin`. Instead, the receipt's `memoSignature` points to an SPL Memo from the verifier. Its transaction log reads `Memo (len 74): "kept:fail:<receipt hash>"`.

**In the app**, **Audit the Keeper** on the "day kept" screen does the same steps on the phone. It fetches the receipts (from Supabase Storage first, with KEPT's backend as a fallback), re-hashes them and compares the result with the `CheckinRecorded` event. The test is `frontend/src/__tests__/keeperAudit.test.ts`.

## 8. How proof works, from the current code

**Photo habit** (a book, a water bottle, …). Code: `backend/src/v4/keeper.ts`, `backend/src/routes/proofVerify.ts`.

1. **Challenge.** `POST /api/proof/challenge` takes the hand gesture (thumbs up, victory or open palm) from the first byte of `sha256(latest blockhash)`, modulo the gestures still allowed (a new challenge never repeats the previous gesture). It records the slot and blockhash, so the server can't pick the gesture. If the RPC can't be reached, it falls back to a random gesture and records no slot. The challenge expires in two minutes.
2. **Judge.** The app uploads the live photo to `POST /proof/verify`. The server hashes the photo and asks the vision model three things: is the object there, is the gesture there, and is it a photo of a screen or a printout. **Any verdict the app sends is ignored.** The photo itself is not stored; only its hash is.
3. **Receipt.** The verdict becomes a receipt with these fields: `v`, `kind`, wallet, Oath (`target`), day, habit, `photoSha256`, what the model was asked to see (`expected`), challenge {gesture, slot, blockhash, issuedAt}, model, verdict, pass and `checkedAt`. Its SHA-256 over canonical JSON is public at `GET /keeper/receipts/<hash>` and as a file on Supabase Storage.
4. **On chain.** When every habit of the day has a passing receipt, the verifier signs `record_checkin` with `proof_hash = sha256(receipt hashes in habit order)`. A failed check's receipt hash goes into an SPL Memo, `kept:fail:<hash>`, from the same key.

**Live activity** (push-ups, squats, jumping jacks, lunges, sit-ups, high knees, burpees, overhead presses, and a timed plank in seconds). Code: `frontend/src/screens/proof/RepSet.tsx`, `packages/engine/src/reps.ts`, `backend/src/v4/repProof.ts`.

1. **Counting.** The phone counts live with an on-device pose model (MediaPipe) from any horizontal angle. The Keeper counts aloud, with hype lines between reps (a Settings switch turns on the no-filter version). The phone uploads the whole pose trace.
2. **The freeze rep.** The challenge also names a rep, picked with `sha256("kept:freeze:<blockhash>:<issuedAt>")[0]` and placed between 30% and 70% of the target. At that rep the Keeper says **"Freeze! One hand up. Hold it."** and the phone takes the photo.
3. **The server recounts the trace** with the same engine. It refuses the set if:
   - it is for the wrong exercise;
   - it takes longer than the challenge allows (at most 240 s);
   - the pose stays frozen for more than a second;
   - there is a gap of more than 2 s;
   - the sample rate is off;
   - the frame shape doesn't match the photo;
   - the count is short of the target;
   - the freeze is missing, too short or too long, comes at the wrong rep, or doesn't sit between two reps;
   - the photo isn't the freeze frame;
   - the trace already passed once ("That rep set was already used").
4. **The AI judges the freeze photo:** it must show a real person mid-activity with one hand raised. The receipt also carries the recount: engine, exercise, target, `repCount`, `phoneCount`, duration, `traceSha256`, freeze and keyframes. The cheats the release refuses are half reps, knee push-ups, piked hips, waist-bend squats, one-arm jacks, frozen poses and replayed sets.
5. **Pose traces are kept privately** (bucket `rep-traces`: body keypoints and timings only, with no image and no wallet) so the counter can be tuned on real sets.

**Other safeguards:**

- There is a limit of 20 checks per wallet per UTC day (`DAILY_PHOTO_CHECKS`).
- A photo or trace that already passed can't be used again.
- Before the wallet opens, the Keeper reads out what the transaction does and roughly how much SOL it moves ("about 0.07 SOL"). A "Stop the Keeper" button silences it.
- Supabase Realtime pushes a friend's proof to everyone's screen in the Oath.

**What this does not prove:**

- The model can be wrong. §5 shows one false negative. Live has no appeal yet; that time a retry passed.
- The photo itself is not public.
- Three gestures are not proof of freshness on their own.
- The pose trace comes from the phone, so a modified app could make up a moving trace. What ties a set to a real person is the freeze photo: live, a raised hand, at the rep the server picked. Photos are deduplicated by exact bytes only.

## 10. Known limits

- Devnet only, with test SOL. The program is built with `debug-tools`, which allows 2-minute days for tests and demos. Seeker Genesis verification is mocked on Devnet with an allowlist; the hosted API's lets any wallet in (a freshly generated wallet signed in to the hosted API and `/api/me` returned `genesis: true, mocked: true`, so the hosted Devnet allowlist lets any wallet in). There is no `set_verifier` instruction yet.
- Counting: keep the phone level and low. A camera looking down from above weakens counting.
- Filmed from behind and to the side, with the feet hidden, knees-down push-ups and planks can't be told apart from full ones. High knees filmed exactly side-on can miss lifts.
- Phantom shows "identity could not be verified" for the default app identity. Settings › "Wallet identity: KEPT's own site" uses KEPT's verified site instead.
- KEPT is not yet listed in the Solana dApp Store.
